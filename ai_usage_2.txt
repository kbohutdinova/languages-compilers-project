# AI Usage Disclosure — Project Stage 2

I used ChatGPT (OpenAI) during Stage 2 of the KameLang compiler project.
AI was used to help understand the assignment requirements, extend the language, implement the compiler, prepare tests, debug errors, and improve the project documentation.

## 2. Parts of the Work Completed with AI Assistance

### Language Design and Grammar
ChatGPT helped extend the Stage 1 grammar with functions, structures, member functions, input, and output operations.
The new syntax includes `action` for functions, `shape` for structures, `give` for returning values, and `read()` and `print()` for input and output.
The existing Stage 1 syntax was preserved to maintain compatibility with previously valid programs.

### Lexer, Parser, and AST
ChatGPT generated updated versions of `compiler.py` with additional tokens, AST nodes, and parser methods.
The implementation includes function declarations, parameters, return statements, structure declarations, object creation, field access, member function calls, and expressions.
Most of the initial implementation was copied from ChatGPT responses and used as the basis for the project.

### Semantic Analysis
ChatGPT helped implement `src/semantic.py`, including symbol tables, scope management, type checking, mutability checking, integer overflow validation, and semantic rules for functions and structures.
The implementation was developed in several versions. When tests failed, I shared the error messages with ChatGPT and used the suggested fixes.

### LLVM Code Generation
ChatGPT generated the initial implementation of `src/codegen.py` using `llvmlite.ir`.
This part generates LLVM IR for variables, expressions, conditions, functions, structures, member functions, and input/output operations.
The code was used as a starting implementation and tested locally.
### Testing
ChatGPT helped prepare `test_semantic.py`, `run_stage2_tests.py`, and the Stage 2 test programs.
The tests cover valid and invalid programs, type errors, incorrect function arguments, mutability violations, integer overflow, structures, and function calls.
I ran the tests locally and shared the results with ChatGPT to identify and correct problems.

### Documentation
ChatGPT helped prepare and update `grammar.ebnf`, `README.md`, and the project setup instructions.
I used the documentation to understand how to build, test, and run the compiler.

## 4. What Was Changed and Why
During development, I tested the compiler locally and identified several problems.
**AST class placement:** Some AST classes were initially placed inside another class because of incorrect indentation. The implementation was corrected so that the classes could be accessed independently.
**Parser implementation:** The parser initially failed when processing mutable structure objects, such as `Point mut p {10, 20};`. Updated versions of the parser fixed the recognition of structure declarations and object initialization.
**Duplicate parser methods:** A duplicated `parse_return()` method was identified and removed.
**Semantic analysis:** Several tests initially failed because structure initialization values were incorrectly compared with the structure type instead of the individual field types. Corrected versions of `compiler.py` and `semantic.py` were used to resolve these failures.
**Python project structure:** I created the `src` directory and organized the semantic analyzer and code generator into separate modules.
**Python environment:** I created a virtual environment because macOS prevented the installation of dependencies into the externally managed Python environment.
**Test organization:** I identified an incorrectly placed `requirements.txt` file inside `tests/err`, which caused the Stage 1 test runner to fail. I removed the unnecessary copy.
Most implementation corrections were suggested or generated by ChatGPT. My direct contributions included running the programs and tests, identifying failures, sharing error output, organizing files, and checking the corrected implementations.
**Runtime overflow handling:** After implementing LLVM code generation, I tested an arithmetic expression that exceeded the signed 32-bit integer range. The initial implementation produced `-2147483648` instead of detecting overflow. I shared the result with ChatGPT and used an updated version of `src/codegen.py` that added runtime overflow checks for integer arithmetic. I then re-ran the test and confirmed that the program printed `integer overflow` and exited with code 1. I also re-ran the existing test suites to verify that the changes did not break previously working features.

## 6. What I Understood

I understand that a compiler has several stages.
The lexer converts source code into tokens. The parser checks the grammatical structure and builds an Abstract Syntax Tree (AST).
Semantic analysis checks whether the program is logically valid. It verifies declared variables, data types, function arguments, scope rules, mutability, and integer overflow.
The symbol table stores information about variables, functions, and structures. It allows the semantic analyzer to find declarations and check how identifiers are used.
LLVM code generation translates the checked AST into LLVM Intermediate Representation. The `llvmlite.ir` library provides a builder API for creating instructions, functions, and basic blocks.
Structures are represented using LLVM structure types. Field access uses field indices, while member functions receive a pointer to the object.
The `read()` and `print()` operations use external C functions such as `scanf` and `printf`.
I also understood why testing is important. A program can have valid syntax but still contain semantic errors, and generated LLVM IR must be executed to confirm that it produces the expected output.
